## 0. การตัดสินใจระหว่างทำ M0

- **เวอร์ชันที่ใช้จริง**: Next.js 16.4, React 19.3, Prisma 7.10 (Prisma 8 ยังเป็น RC), Better Auth 1.7, next-intl 4, Zod 4, shadcn/ui แบบ Base UI
- **ปิด Cache Components / partial prefetching** ใน `next.config.ts` เพราะทุกหน้าเป็นข้อมูลรายผู้ใช้หลังล็อกอิน อ่านข้อมูลใหม่ทุก request
- **ภาษา**: ไม่ใส่ locale ใน URL ใช้ cookie `NEXT_LOCALE` (ค่าเริ่มต้น `th`) โครงสร้างจึงเป็น `src/app/(auth|onboarding|app)/…` แทน `[locale]/`
- **Middleware**: Next 16 เปลี่ยนชื่อเป็น `src/proxy.ts` ใช้แค่เช็คเบื้องต้นว่ามี session cookie สิทธิ์จริงตรวจใน `requireUser()` / `requireRole()`
- **เวลา**: ทุกคอลัมน์ DateTime เป็น `timestamptz` เพื่อให้ SQL รายงานรายเดือนคิดตามเวลาไทยได้ถูก
- **เงิน**: ภาษีเก็บเป็น basis points (`vatRateBp` 700 = 7%) ส่วนราคาสินค้าจะเก็บเป็นจำนวนเต็มหน่วยสตางค์ (ตัดสินใจใน M2)
- **Docker**: เลื่อนไปทำใน M8 เพราะเครื่องพัฒนาไม่ได้เปิด Docker ระหว่างพัฒนาใช้ embedded PostgreSQL ที่ `%USERPROFILE%\quotation-jcp-devdb` (port 55433)
- **Rate limit การล็อกอิน**: 30 ครั้ง/นาที/IP เพราะทั้งออฟฟิศอาจใช้ IP เดียวกัน ส่วนการเดารหัสผ่านถูกกันด้วยการล็อกรายบัญชี
- **ล็อกบัญชีแบบ atomic**: จองสิทธิ์ลองรหัสผ่านด้วย `UPDATE … RETURNING` ก่อนตรวจรหัสผ่าน ยิงพร้อมกันกี่คำขอก็ตรวจรหัสผ่านได้ไม่เกิน 5 ครั้ง
- **endpoint ของ Better Auth ที่ห้ามเรียกจากเบราว์เซอร์**: `/admin/*`, `/update-user`, `/change-password`, `/two-factor/disable` และอื่น ๆ (ดู `src/server/domain/auth-routes.ts`) แอปเรียก endpoint เหล่านี้เฉพาะจากฝั่ง server (`auth.api`) ผ่านการตรวจสิทธิ์ ด่าน onboarding และ audit log ของแอป
- **ผลตรวจ BintzIT รอบ M0**: แก้แล้วทั้งหมด ยกเว้น 2 เรื่องที่ทำใน M8 ตามด้านล่าง

## 0.1 การตัดสินใจระหว่างทำ M1

- **เงิน**: เก็บเป็นจำนวนเต็มหน่วยสตางค์ (`listPriceSatang`, `minPriceSatang`) แปลงด้วย `parseBahtToSatang` / `formatSatang` ใน `src/server/domain/money.ts` ไม่ใช้ float
- **การมองเห็นลูกค้าของพนักงานขาย**:
  - เห็นรายละเอียดเต็มเฉพาะลูกค้าของตัวเอง และลูกค้าที่ยังไม่มีผู้ดูแล (สถานะปกติ)
  - ลูกค้าของคนอื่นเห็นแค่ชื่อ สาขา และชื่อผู้ดูแล เลขผู้เสียภาษีและเบอร์โทรถูกตัดออกตั้งแต่ฝั่ง server
  - แก้ไขได้เฉพาะลูกค้าของตัวเอง
- **ลูกค้าที่ผู้บริหาร/แอดมินสร้าง**: เลือกผู้ดูแลได้ หรือปล่อยว่างไว้ให้พนักงานขายคนแรกที่ออกใบเสนอราคาเป็นผู้ดูแล (ทำใน M2)
- **ราคาขั้นต่ำ**: ไม่ถูก select จากฐานข้อมูลเลยเมื่อผู้ใช้เป็นพนักงานขาย (`src/server/services/products.ts`) มี smoke test ตรวจว่าไม่มีค่าหลุดไปในหน้าเว็บหรือ RSC payload
- **เลขผู้เสียภาษี**: ตรวจหลักตรวจสอบ (mod 11) ทั้งตอนกรอกและตอนนำเข้า และฐานข้อมูลมี CHECK constraint (13 หลัก, นิติบุคคลต้องมี, รหัสสาขา 5 หลัก, ราคาขั้นต่ำ ≤ ราคาปกติ)
- **นำเข้า Excel**:
  - ขั้นตอนเป็นตรวจไฟล์ก่อน แล้วค่อยยืนยัน ตอนยืนยันระบบคำนวณแผนใหม่ใน transaction เดียวกับการบันทึก
  - ลูกค้าเดิมเติมเฉพาะช่องที่ว่าง ไม่เขียนทับ
  - เก็บรหัสลูกค้า Express แยกรายบริษัท (`CustomerExpressCode`) ใช้จับคู่บุคคลธรรมดาที่ไม่มีเลขภาษี และใช้กับการนำเข้าวันขายล่าสุดใน M6
  - รหัสพนักงานขายที่ไม่พบในระบบ → ลูกค้าไม่มีผู้ดูแล และแสดงเตือนในหน้าตรวจไฟล์
  - Excel มักเก็บเลขภาษี/รหัสสาขาเป็นตัวเลขจนเลข 0 นำหน้าหาย ระบบเติมคืนให้ และแม่แบบตั้งคอลัมน์เหล่านี้เป็นข้อความ
  - จำกัดไฟล์ 8 MB / 20,000 แถว (server action รับได้ 10 MB) และตรวจขนาดหลังแตก zip จาก central directory ก่อนเปิดไฟล์ (≤ 100 MB, ≤ 500 entries) กัน zip bomb
  - **ลูกค้ารอเลือกผู้ดูแล = ไม่มีผู้ดูแลเสมอ** มี CHECK constraint ในฐานข้อมูล ผู้ดูแลเดิมถูกบันทึกเป็นผู้มีสิทธิ์เลือก (candidate)
  - **นำเข้าซ้ำไม่เปิดเรื่องที่ตัดสินแล้ว**: ถ้าผู้ดูแลมาจากการตัดสินของคน (สร้างเอง / โอน / ผู้บริหารเลือก / ออกใบเสนอราคาคนแรก) ไฟล์ที่ระบุพนักงานขายต่างกันจะขึ้นแค่คำเตือนในหน้าตรวจไฟล์
  - รหัส Express ที่ชี้ไปลูกค้าคนละรายกับเลขภาษี → แถวนั้นเป็นข้อผิดพลาด ไม่ทำให้การนำเข้าทั้งไฟล์ล้ม
  - บันทึกแบบ batch (`createMany` ครั้งละ 1,000 แถว) ทดสอบไฟล์ 20,000 แถวบนเครื่องพัฒนา: ตรวจไฟล์ 2 วินาที, นำเข้า 16 วินาที (transaction timeout 5 นาที) ต้องวัดซ้ำบนฐานข้อมูล production ใน M8
- **ค้นหาด้วยเลขผู้เสียภาษี**: พนักงานขายค้นแบบขึ้นต้นด้วยตัวเลขได้เฉพาะลูกค้าที่ตัวเองเปิดดูได้ ส่วนลูกค้าคนอื่นต้องพิมพ์ครบ 13 หลักจึงจะพบ กันการไล่เดาเลขทีละหลัก
- **คำเตือนลูกค้าอาจซ้ำ**: บุคคลธรรมดาเทียบชื่อ (ตัดคำนำหน้าและช่องว่าง) และเบอร์โทร (ตัดขีด/ช่องว่าง) ใน SQL ส่วนนิติบุคคลที่เลขภาษีเดียวกันแต่สาขาต่างจะขึ้นเตือนให้ยืนยัน และจะตรวจซ้ำเฉพาะตอนข้อมูลระบุตัวตนเปลี่ยน

## 0.2 การตัดสินใจระหว่างทำ M2

- **ใครเห็นใบเสนอราคา**: เจ้าของใบ (พนักงานขาย) และผู้บริหารเท่านั้น แอดมินไม่เห็น เว้นแต่มีบทบาทผู้บริหารด้วย ส่วนการสร้างใบต้องมีบทบาทพนักงานขาย (ผู้บริหารที่ขายเองให้เพิ่มบทบาทพนักงานขาย)
- **หน่วยที่เก็บ**:
  - เงินเป็นสตางค์ ยอดรวมเป็น `BigInt`
  - จำนวนเป็นหนึ่งในพัน (`quantityMilli`: 1.5 ม้วน = 1500) ทศนิยมได้ 3 ตำแหน่ง
  - ส่วนลด % เป็น basis points
  - ยอดรวมต่อใบไม่เกิน 10,000 ล้านบาท เพื่อให้ผลรวมเป็นจำนวนเต็มที่ปลอดภัยใน JavaScript
- **การคำนวณ** (`src/server/domain/pricing.ts` ใช้ทั้ง server และหน้าจอ):
  - ปัดเศษครึ่งขึ้นเป็นสตางค์ 3 จุดเท่านั้น: ราคา × จำนวน, ส่วนลด %, และ VAT
  - ส่วนลดบาทรายบรรทัด = ลดจากยอดของบรรทัด
  - ส่วนลดท้ายบิลกระจายลงทุกบรรทัดตามสัดส่วนยอด (largest remainder ผลรวมตรงทุกสตางค์) ก่อนเทียบราคาขั้นต่ำ
  - เทียบราคาขั้นต่ำแบบไม่หาร (`ยอดสุทธิ × 1000 < ราคาขั้นต่ำ × จำนวน`) จึงไม่มีช่องโหว่จากการปัดเศษ
- **ต้องขออนุมัติเมื่อ**:
  - ราคาสุทธิต่ำกว่าราคาขั้นต่ำ
  - เป็นบรรทัดพิมพ์เอง
  - สินค้าที่ไม่ใช่รายการบริการแต่ไม่มีราคาขั้นต่ำ
- **ขั้นอนุมัติทำใน M4**: ใน M2 ใบที่ต้องขออนุมัติบันทึกเป็นร่างได้ แต่กด "ส่งลูกค้าแล้ว" ไม่ได้
- **หน้าจอเตือน "ต้องขออนุมัติ"**:
  - ระหว่างกรอก หน้าจอถาม server ทุก 0.6 วินาทีหลังหยุดพิมพ์
  - server ตอบแค่เหตุผลรายบรรทัด ไม่ส่งราคาขั้นต่ำ
  - พนักงานขายยังลองราคาไล่หาเกณฑ์ได้ ซึ่งเลี่ยงไม่ได้ตามความต้องการที่ให้ระบบบอกว่าต้องขออนุมัติ
- **ข้อมูลที่ server เชื่อ**: ชื่อสินค้า หน่วย ราคาปกติ และราคาขั้นต่ำอ่านจากตารางสินค้าทุกครั้ง หน้าจอส่งมาแค่รหัสสินค้า จำนวน ราคา และส่วนลดตามที่พิมพ์ แล้ว server คำนวณยอดใหม่ทั้งหมด
- **เลขที่เอกสาร**:
  - `QT-<รหัสบริษัท>-<YYMM เวลาไทย>-<0001>` ออกด้วย upsert แบบ atomic บน `doc_sequence` ใน transaction เดียวกับการบันทึก
  - smoke test ยิงพร้อมกัน 40 ครั้งได้เลขไม่ซ้ำ
  - เลขที่ยกเลิกแล้วไม่ถูกนำกลับมาใช้
  - เปลี่ยนบริษัทหลังออกเลขแล้วไม่ได้
- **วันที่ในใบ**: เป็นวันที่บันทึกฉบับร่างครั้งล่าสุด และเปลี่ยนเป็นวันที่กด "ส่งลูกค้าแล้ว" วันยืนราคาคำนวณจากวันนั้น ส่วนเดือนในเลขที่คงเป็นเดือนที่สร้างใบ
- **สถานะใน M2**:
  - ร่าง → ส่งลูกค้าแล้ว
  - แก้ไขเป็นฉบับใหม่: กลับเป็นร่างด้วยเลขเดิม + `-R1`, `-R2`
  - คัดลอก: ได้เลขใหม่ ราคาสินค้าเป็นราคาปัจจุบัน ส่วนลดคงเดิม สินค้าที่ปิดการขายไม่ถูกคัดลอก
  - ยกเลิก: ใส่เหตุผลได้
- **ประวัติการส่ง**: ทุกครั้งที่กด "ส่งลูกค้าแล้ว" ระบบเก็บสำเนาข้อมูลของฉบับนั้นใน `QuotationRevision` (PDF จะเพิ่มใน M3)
- **ข้อมูลลูกค้าในใบ**: คัดลอกชื่อ ที่อยู่ เลขภาษี สาขา และผู้ติดต่อเก็บไว้ในใบตอนบันทึก แก้ข้อมูลลูกค้าภายหลังไม่ทำให้เอกสารที่ส่งไปแล้วเปลี่ยน
- **ลูกค้าที่ยังไม่มีผู้ดูแล**: พนักงานขายคนแรกที่บันทึกใบเสนอราคาได้เป็นผู้ดูแล ระบบล็อกแถวลูกค้า (`FOR UPDATE`) และตรวจสิทธิ์ซ้ำใน transaction พร้อมบันทึกประวัติ `QUOTE_CLAIM`
- **แก้ไขจาก 2 หน้าจอพร้อมกัน**: ใช้คอลัมน์ `version` บันทึกได้เฉพาะฉบับที่หน้าจอโหลดมา
- **CHECK constraint**: ยอดรวมต้องเท่ากับผลบวกของส่วนประกอบ ส่วนลดต้องไม่ติดลบและไม่เกินยอด จำนวนต้องมากกว่า 0 และวันยืนราคาต้องไม่ก่อนวันที่ในใบ
- **ผลตรวจ BintzIT รอบ M2** (แก้แล้วทั้งหมด):
  - ค่าส่วนลดแบบบาทเก็บเป็น `BigInt` (เดิมส่วนลดเกิน 21.47 ล้านบาททำให้บันทึกล้ม)
  - ใบที่บันทึกแล้ว (รวมฉบับ R1, R2) เปลี่ยนลูกค้าไม่ได้ ถ้าจะเสนอให้ลูกค้ารายอื่นให้ใช้การคัดลอก
  - การแก้ไขต้องส่ง `version` มาทุกครั้ง
  - เจ้าของใบต้องยังมีบทบาทพนักงานขายจึงจะเปิดดูหรือทำรายการได้ (ถ้าถูกเปลี่ยนเป็นแอดมินอย่างเดียวจะเห็นไม่ได้)
  - สำเนาใน `QuotationRevision` ไม่เก็บราคาขั้นต่ำ เพราะ M3 อาจนำไปพิมพ์หรือแสดง
  - ฉบับร่างคงบริษัทเดิมแม้ผู้ใช้ถูกถอนสิทธิ์บริษัทนั้นภายหลัง (เลขที่เป็นของบริษัทนั้น) แต่บริษัทต้องยังเปิดใช้งาน
  - หน้าจอแก้ไขบนแท็บเล็ตไม่ล้นจอ ปุ่มบนมือถือขยายเป็น 40px และข้อความหลังคัดลอกบอกชัดว่าบันทึกเป็นฉบับร่างเลขที่ใหม่แล้ว

## 0.3 การตัดสินใจระหว่างทำ M3

- **สร้าง PDF**:
  - ใช้ HTML template (`src/server/pdf/quotation-template.ts` เป็นฟังก์ชันล้วน) แล้วให้ Chrome พิมพ์ผ่าน `puppeteer-core`
  - เครื่องพัฒนาใช้ Chrome ที่ติดตั้งอยู่ ส่วน Docker ใช้ Chromium ของระบบ (`CHROME_PATH`) ไม่ต้องดาวน์โหลด Chrome แยก
  - เปิด browser ไว้ตัวเดียวต่อ process และพิมพ์พร้อมกันได้ไม่เกิน 2 หน้า
- **ฟอนต์**: Sarabun (SIL OFL) จาก `@fontsource/sarabun` ฝังใน PDF เป็น data URI ทั้งภาษาไทยและอังกฤษ ตัวปกติและตัวหนา
- **ความปลอดภัยของหน้าที่พิมพ์**:
  - ปิด JavaScript และบล็อกทุก request ยกเว้น `data:`
  - ทุกค่าจากฐานข้อมูลถูก escape
  - รูปรับเฉพาะ data URI ที่เป็น PNG/JPEG
  - ข้อความท้ายหน้า (หมายเลขหน้า) เป็น ASCII เท่านั้น
- **ลายน้ำ** (`pdfWatermark`): "ฉบับร่าง" เฉพาะใบที่ยังต้องขออนุมัติและยังไม่อนุมัติ "ยกเลิก" สำหรับใบที่ยกเลิก ส่วนใบราคาปกติที่ยังเป็นร่างพิมพ์ได้ไม่มีลายน้ำ เพื่อให้พนักงานขายดาวน์โหลดไปส่งเองแล้วกด "ส่งลูกค้าแล้ว"
- **ไฟล์ที่ส่งลูกค้า**:
  - ทุกครั้งที่ส่งลูกค้า (กดเอง หรือส่งอีเมลจากระบบ) ระบบพิมพ์ PDF ลงวันที่วันนั้นแล้วเก็บไว้กับ revision (`QuotationRevision.pdfKey`)
  - ลิงก์ PDF ของใบที่ส่งแล้วให้ไฟล์เดิมทุกไบต์
  - `snapshot` เก็บข้อมูลเอกสาร (บริษัท ผู้เสนอราคา) โดยไม่เก็บรูปและราคาขั้นต่ำ
- **ภาษาเอกสาร**: เลือกรายใบ (`pdfLanguage`)
  - ฉบับอังกฤษใช้ชื่อและที่อยู่บริษัทภาษาอังกฤษ ชื่อสินค้าภาษาอังกฤษ (เก็บไว้ในบรรทัดตอนบันทึก) และยอดเงินเป็นตัวหนังสืออังกฤษ
  - ฉบับไทยใช้ปี พ.ศ.
- **ส่งอีเมล**:
  - ผู้ส่งเป็นชื่อและอีเมลผู้ส่งของบริษัท และ Reply-To เป็นอีเมลพนักงานขาย
  - ส่งถึงได้ 5 อีเมล และสำเนาถึงได้อีก 5 อีเมล
  - จำกัด 30 ฉบับต่อคนต่อชั่วโมง
  - ส่งใน transaction เดียวกับการเปลี่ยนสถานะ: ส่งไม่สำเร็จ → สถานะไม่เปลี่ยนและลบ PDF ที่เพิ่งสร้าง
  - ประวัติอยู่ใน `QuotationEmail`
- **ผู้ให้บริการอีเมล**:
  - เรียก Resend ผ่าน REST เมื่อมี `RESEND_API_KEY`
  - เครื่องพัฒนาที่ไม่มี key เขียนอีเมลลง `storage/outbox/`
  - production ที่ไม่มี key จะไม่ยอมส่ง
  - ชื่อผู้ส่งตัดอักขระที่ใช้แทรก header ได้ และหัวเรื่องเป็นบรรทัดเดียว
- **ไฟล์ส่วนตัว** (`src/server/storage.ts`):
  - เก็บนอก `public/` ใน `STORAGE_DIR` (เครื่องพัฒนาคือ `./storage` ที่ git ไม่เก็บ)
  - key สร้างโดย server และสุ่มเสมอ (ตรวจรูปแบบกัน path traversal) และไม่เขียนทับไฟล์เดิม
  - ส่งไฟล์ออกผ่าน route ที่ตรวจสิทธิ์เท่านั้น
- **รูปที่อัปโหลด**:
  - โลโก้บริษัท (แอดมิน) และลายเซ็นของพนักงานขาย (เจ้าตัว)
  - รับเฉพาะ PNG/JPEG ตรวจจากไบต์จริง ขนาดไม่เกิน 1 MB และไม่รับ SVG
  - โลโก้เปิดดูได้ทุกคนที่ล็อกอิน ลายเซ็นเปิดดูได้เฉพาะเจ้าตัวและแอดมิน
- **build แบบ standalone**: ใส่ `turbopackIgnore` ที่การอ่านเขียนไฟล์ใน storage และตั้ง `outputFileTracingExcludes` (storage, .env, tests) ไม่ให้ไฟล์ส่วนตัวเข้า bundle ส่วนฟอนต์ใส่ด้วย `outputFileTracingIncludes`
- **ผลตรวจ BintzIT รอบ M3** (แก้แล้วทั้งหมด):
  - **วันที่ใน PDF**: PDF ของใบที่ยังไม่ส่งพิมพ์วันที่เป็นวันนี้และคำนวณวันยืนราคาจากวันนี้ ใช้กฎเดียวกับตอนกดส่ง ไฟล์ที่ดาวน์โหลดไปส่งเองในวันเดียวกันจึงตรงกับไฟล์ที่ระบบเก็บ และกล่องยืนยันบอกว่าหากส่งก่อนวันนี้ให้ดาวน์โหลดไฟล์ใหม่
  - **ลำดับการส่งอีเมล**: ส่งเป็นขั้นตอนสุดท้ายของ transaction หลังบันทึกทุกอย่างแล้ว และส่ง `Idempotency-Key` (เลขใบ + version) ให้ Resend ส่วนกรณีส่งออกไปแล้วแต่บันทึกไม่สำเร็จ ระบบไม่ลบ PDF แต่บันทึก log พร้อมรายละเอียด และบอกผู้ใช้ว่าอย่าส่งซ้ำ
  - **รูปที่อัปโหลด**: ตรวจขนาดพิกเซลจาก header ของ PNG/JPEG (ด้านละไม่เกิน 4,000 พิกเซล รวมไม่เกิน 12 ล้านพิกเซล) กันไฟล์เล็กที่ประกาศขนาดภาพมหาศาล
  - **คิวสร้าง PDF**: จำกัดคิวรอ 20 งาน และรอได้ไม่เกิน 30 วินาที เกินแล้วตอบ 503 ส่วน PDF ที่ต้องพิมพ์ใหม่จำกัด 20 ครั้งต่อคนต่อนาที (ไฟล์ที่เก็บไว้แล้วไม่นับ)
  - **บริษัทที่ไม่จด VAT**: PDF ไม่แสดงแถวภาษีมูลค่าเพิ่ม และอีเมลไม่เขียนว่า "รวมภาษีมูลค่าเพิ่ม"
  - **dialog บนมือถือ**: สูงไม่เกินจอและเลื่อนดูได้
  - **ใบที่ยกเลิก**: ไฟล์ของฉบับที่เคยส่งยังเปิดได้ในฐานะหลักฐาน โดยหน้าจอแจ้งว่าใบนี้ยกเลิกแล้ว
  - ปรับถ้อยคำภาษาไทยให้เป็นทางการ

## 0.4 การตัดสินใจระหว่างทำ M4

- **ตัดสินใจร่วมกับผู้ใช้ (25 พ.ย. 2026)**:
  - "เสนอราคาใหม่": ระบบเปลี่ยนราคาในใบเป็นราคาที่ผู้บริหารเสนอแล้วถือว่าอนุมัติทันที ไม่ต้องให้พนักงานขายกดยอมรับ
  - เวลาทำการสำหรับเตือนคำขอค้าง: จันทร์–ศุกร์ 08:30–17:30 เวลาไทย ยังไม่นับวันหยุดนักขัตฤกษ์
  - ผู้บริหารที่ออกใบเสนอราคาเองด้วยพิจารณาคำขอของตัวเองได้ ระบบบันทึกว่า "ผู้ขอพิจารณาเอง" ทั้งในประวัติและ audit log
- **ผู้อนุมัติ**: ผู้ใช้ทุกคนที่มีบทบาทผู้บริหาร ได้รับแจ้งทั้งหมด และใครพิจารณาก่อนก็ได้ ระบบ claim คำขอด้วยเงื่อนไข `status = PENDING` จึงพิจารณาซ้อนกันไม่ได้
- **สถานะ**:
  - ร่าง (ต่ำกว่าขั้นต่ำ) → ขออนุมัติ → รออนุมัติ
  - ผู้บริหารพิจารณาแล้ว → อนุมัติแล้ว / ไม่อนุมัติ (ต้องใส่เหตุผล)
  - ระหว่างรออนุมัติ แก้ไขหรือส่งลูกค้าไม่ได้ ถอนคำขอได้ (กลับเป็นร่าง) และถ้ายกเลิกใบ คำขอจะถูกถอนให้อัตโนมัติ
  - ใบที่ไม่อนุมัติแก้ไขแล้วขอใหม่ได้
  - คำขอที่รอพิจารณามีได้ใบละ 1 คำขอ (partial unique index ในฐานข้อมูล)
- **แก้ราคาหลังอนุมัติ** (`src/server/domain/approvals.ts`):
  - ตอนพิจารณา ระบบเก็บราคาสุทธิต่อหน่วยของทุกบรรทัดที่ต้องอนุมัติไว้ใน `approvedLines`
  - แก้ไขภายหลังยังคงสถานะ "อนุมัติแล้ว" ถ้าทุกบรรทัดที่ต้องอนุมัติยังมีราคาสุทธิต่อหน่วยไม่ต่ำกว่าที่อนุมัติ (สินค้าเดิม หรือรายการพิมพ์เองที่ชื่อและหน่วยเดิม) ถ้าต่ำกว่าจะกลับเป็นร่างและต้องขอใหม่
  - เทียบแบบคูณไขว้ ไม่มีการปัดเศษ
  - การแก้ไขเป็นฉบับใหม่ (R1, R2) ใช้กฎเดียวกัน ส่วนการคัดลอกได้ใบใหม่ที่ต้องขออนุมัติใหม่
- **เสนอราคาใหม่**: ผู้บริหารกำหนดราคาต่อหน่วยได้เฉพาะบรรทัดที่ต้องอนุมัติ แล้ว server คำนวณยอดทั้งใบใหม่ (ส่วนลด ส่วนลดท้ายบิล VAT) และบันทึกว่าเปลี่ยนจากราคาเท่าไรเป็นเท่าไร
- **การมองเห็น**: หน้าพิจารณา (`/approvals`) เปิดได้เฉพาะผู้บริหาร และแสดงราคาขั้นต่ำ ประวัติการขออนุมัติในหน้าใบเสนอราคาไม่แสดงราคาขั้นต่ำ เพราะพนักงานขายเห็นหน้านี้ด้วย
- **แจ้งเตือน**:
  - กระดิ่งในระบบ (ตาราง `Notification`) บันทึกใน transaction เดียวกับการเปลี่ยนสถานะ
  - อีเมลส่งหลัง commit ทีละผู้รับ ถ้าส่งไม่สำเร็จจะบันทึก log แต่ไม่ย้อนการเปลี่ยนสถานะ
  - เมื่อคำขอถูกพิจารณาหรือถอน การแจ้งเตือน "ขออนุมัติ" ของผู้บริหารถูกทำเป็นอ่านแล้ว
- **ผลตรวจ BintzIT รอบ M4** (แก้แล้วทั้งหมด):
  - **ช่องเสนอราคาใหม่**: ระบุชัดว่าเป็นราคาก่อนส่วนลด และแสดงราคาสุทธิหลังส่วนลดกับยอดรวมใหม่ก่อนยืนยัน คำนวณด้วยฟังก์ชันเดียวกับ server
  - **หน้าคำขอที่พิจารณาแล้ว**: แสดงรายการและยอดรวม ณ เวลาที่ขอ ไม่ใช่ข้อมูลปัจจุบันของใบ
  - **ลำดับการล็อก**: การพิจารณาล็อกแถวใบเสนอราคาก่อน ตรงกับการถอน การยกเลิก และการแก้ไข จึงไม่เกิด deadlock
  - **ยกเลิกใบที่รออนุมัติ**: แจ้งผู้บริหารด้วย
  - **รายการพิจารณาแล้วล่าสุด**: เรียงตามวันที่พิจารณา
  - ปรับถ้อยคำ
- **เตือนคำขอค้าง**: `POST /api/cron/approval-reminders` พร้อม `Authorization: Bearer CRON_SECRET` (ไม่ตั้ง secret = endpoint ไม่มีอยู่) ทุก 15 นาที เตือนทุก 4 ชั่วโมงทำการนับจากคำขอหรือการเตือนครั้งก่อน และ claim ทีละคำขอ รันซ้อนกันก็ไม่เตือนซ้ำ

## 0.5 การตัดสินใจระหว่างทำ M5

- **ตัดสินใจร่วมกับผู้ใช้ (25 พ.ย. 2026)**:
  - Won นับยอดเต็มใบ (ยอดก่อน VAT) ถ้าลูกค้าสั่งไม่ครบทุกรายการ ต้องแก้เป็นฉบับใหม่ให้ตรงกับ PO ก่อน
  - ตอนกด Won บังคับเลขที่ PO และวันที่ PO ส่วนไฟล์ PO (PDF/JPG/PNG ไม่เกิน 10 MB) ไม่บังคับ แนบภายหลังได้ครั้งเดียว
  - Won และ Lost ย้อนกลับไม่ได้ทุกบทบาท ถ้าบันทึกผิดต้องคัดลอกเป็นใบใหม่
  - ใบที่หมดอายุแล้วยังกด Won/Lost ได้ถ้ายืนราคาเดิม ถ้าจะเปลี่ยนราคาหรือวันยืนราคาให้แก้เป็นฉบับใหม่
- **สิทธิ์**: เจ้าของใบ (ที่ยังมีบทบาทพนักงานขาย) เป็นผู้บันทึกการติดตามและกด Won/Lost ได้เฉพาะใบที่ "ส่งลูกค้าแล้ว" หรือ "หมดอายุ" ผู้บริหารดูได้แต่ไม่บันทึกแทน
- **การติดตามระดับใบ** (ตาราง `Followup`): บันทึกเป็น log แก้หรือลบไม่ได้ วันนัดถัดไปของรายการล่าสุดเก็บไว้ที่ `quotation.nextFollowupOn` และวันที่ติดต่อล่าสุดที่ `lastFollowupAt` รายการที่บันทึกย้อนหลัง (วันที่ติดต่อเก่ากว่ารายการล่าสุด) ไม่เปลี่ยนวันนัดและวันที่ติดต่อล่าสุด
- **แก้ไขเป็นฉบับใหม่**: วันนัดติดตามเดิมยังอยู่ (นัดกับลูกค้า ไม่ได้ผูกกับฉบับ) ระหว่างเป็นร่างจะไม่ขึ้นในรายการ และเมื่อส่งใหม่ ถ้าวันนัดผ่านไปแล้วจะขึ้นเป็น "เลยกำหนด"
- **การติดต่อระดับลูกค้า**: `Followup` ที่ไม่มี `quotationId` วันนัดถัดไปเก็บที่ `customer.nextFollowupOn` บันทึกได้เฉพาะผู้ดูแลลูกค้า และเห็นได้เฉพาะผู้ดูแลปัจจุบัน ผู้บริหาร และแอดมิน (ลูกค้าที่ไม่มีผู้ดูแล พนักงานขายคนอื่นจะไม่เห็นบันทึกของผู้ดูแลเดิม)
- **หน้าแรกของพนักงานขาย**:
  - "ต้องติดตามวันนี้ / เลยกำหนด": ใบ "ส่งลูกค้าแล้ว/หมดอายุ" และลูกค้าที่วันนัดถัดไปถึงแล้ว
  - "ส่งแล้วไม่มีการติดตามเกิน 7 วัน": ใบ "ส่งลูกค้าแล้ว" ที่ไม่ได้นัดไว้ และวันที่ส่งหรือวันที่ติดต่อล่าสุด (ที่ใหม่กว่า) ผ่านมาเกิน 7 วันตามปฏิทินไทย (ส่งวันที่ 18 ขึ้นวันที่ 26) ใบที่นัดไว้แล้วแต่เลยวันนัดจะอยู่ในรายการ "เลยกำหนด" แทน และได้กระดิ่งเตือนเมื่อไม่มีการติดต่อเกิน 7 วัน ส่วนใบที่นัดไว้วันนี้หรือหลังจากนี้ไม่ถูกเตือน
  - "ลูกค้าที่หายไป" ทำแล้วใน M6 (ดูหัวข้อ 0.6)
- **วันที่**: วันที่ติดต่อ วันนัด วันที่ PO และวันยืนราคาเป็นคอลัมน์ DATE นับตามวันในเวลาไทย หมดอายุเมื่อเลยวันยืนราคาไปแล้ว (วันยืนราคาวันสุดท้ายยังไม่หมดอายุ)
- **งานรายวัน**: `POST /api/cron/daily` (เดิมชื่อ quotations-daily, Bearer `CRON_SECRET`) เปลี่ยนใบ "ส่งลูกค้าแล้ว" ที่เลยวันยืนราคาเป็น "หมดอายุ" แล้วแจ้งกระดิ่งเจ้าของ และแจ้งกระดิ่ง "ไม่มีการติดตามเกิน 7 วัน" ครั้งเดียวต่อช่วงที่เงียบ ทุกการเปลี่ยนแปลงใช้ update แบบมีเงื่อนไข รันซ้ำหรือรันซ้อนกันก็ไม่แจ้งซ้ำ
- **ไฟล์ PO**: ตรวจชนิดจากเนื้อไฟล์ (PDF/PNG/JPEG) เก็บใน storage ส่วนตัว เปิดได้ผ่าน `/quotations/[id]/po` เฉพาะคนที่เห็นใบนั้น ไฟล์ PDF ที่ผู้ใช้อัปโหลดถูกส่งเป็นไฟล์ดาวน์โหลด ไม่เปิดแสดงในเบราว์เซอร์ ขนาด body ของ server action และ proxy ตั้งไว้ 12 MB
- **ฐานข้อมูล**: CHECK constraint บังคับว่า Won ต้องมีเลขที่และวันที่ PO, Lost ต้องมีเหตุผล (เลือก "อื่น ๆ" ต้องมีรายละเอียด), และวันนัดถัดไปต้องไม่ก่อนวันที่ติดต่อ
- **ผลตรวจ BintzIT รอบ M5** (ไม่พบระดับ critical/high แก้แล้วทั้งหมด):
  - **บันทึกย้อนหลังลบวันนัด**: เดิมรายการย้อนหลังที่ไม่ใส่วันนัดทำให้วันนัดที่ตั้งไว้หายไป ตอนนี้เปลี่ยนวันนัดเฉพาะเมื่อเป็นการติดต่อล่าสุด
  - **ไฟล์ PO ใหญ่เกิน**: ตรวจขนาดในเบราว์เซอร์ก่อนส่ง แทนที่จะให้หน้าแสดงข้อผิดพลาด
  - **audit log**: การหมดอายุอัตโนมัติบันทึกใน audit log ในนามระบบ
  - **วันที่และเงื่อนไข**: วันที่ติดต่อล่าสุดแสดงตามวันในเวลาไทย, เงื่อนไข 7 วันเปลี่ยนเป็น "เกิน 7 วัน" ตามข้อกำหนด, การ claim กระดิ่งตรวจวันที่ส่งด้วย
  - ปรับถ้อยคำภาษาไทยให้เป็นทางการและตรงกับชื่อปุ่ม และขยายปุ่มเล็กให้แตะง่ายบนมือถือ

## 0.6 การตัดสินใจระหว่างทำ M6

- **ตัดสินใจร่วมกับผู้ใช้ (25 พ.ย. 2026)**:
  - ลูกค้าที่ยังไม่เคยซื้อเลย นับว่าหายไปเมื่อเพิ่มเข้าระบบมาเกินระยะเวลาที่กำหนด (นับจากวันที่สร้างลูกค้า)
  - "ยอดซื้อเดิม" = ยอด Won (ก่อน VAT) ในช่วง 12 เดือนจนถึงวันที่ซื้อล่าสุด ถ้าไฟล์ Express มียอดขาย 12 เดือน ใช้ค่าที่มากกว่า
  - ลูกค้าที่บันทึกว่าเสียไปแล้ว ผู้ดูแลกด "กลับมาเป็นลูกค้า" เองได้ และกลับอัตโนมัติเมื่อนำเข้าไฟล์ Express ที่มีวันขายหลังวันที่บันทึกว่าเสียไป
  - ลูกค้าของพนักงานขายที่ถูกปิดบัญชีแล้ว พนักงานขายคนอื่นกด "ขอรับดูแลลูกค้า" ได้ทันที แม้ลูกค้ายังซื้อไม่ถึงระยะเวลาที่กำหนด
- **ไม่เคลื่อนไหว**: `customer.lastPurchaseDate` = วันที่ใหม่กว่าระหว่างวันที่ Won ล่าสุด (วันในเวลาไทยที่กด Won) กับวันที่ขายล่าสุดจาก Express ลูกค้า "หายไป" เมื่อวันอ้างอิง (วันซื้อล่าสุด หรือวันที่เพิ่มลูกค้าถ้ายังไม่เคยซื้อ) ผ่านมา **เกิน** N เดือน (ซื้อ 25 พ.ค. ครบ 6 เดือน 25 พ.ย. ขึ้นรายการ 26 พ.ย.) เดือนที่มีวันน้อยกว่าใช้วันสุดท้ายของเดือน ค่า N ตั้งที่หน้า "ตั้งค่า" (แอดมิน 1–36 เดือน ค่าเริ่มต้น 6) เก็บในตาราง `Setting`
- **การแจ้งผู้ดูแล 3 ทาง**:
  - กระดิ่งครั้งเดียวต่อช่วงที่หายไป (งานรายวันทุกชั่วโมง) ถ้าผู้ดูแลคนเดียวมีลูกค้าหายไปพร้อมกันเกิน 3 ราย (เช่น หลังนำเข้าไฟล์ Express ครั้งแรก) ส่งกระดิ่งสรุปครั้งเดียว
  - หน้าแรก "ลูกค้าที่หายไป" เรียงจากหายไปนานที่สุด แสดงวันที่ซื้อล่าสุด ยอดซื้อเดิม และใบเสนอราคาที่ยังเปิดอยู่ (ใบเสนอราคาและบันทึกการติดต่อไม่นับว่าเคลื่อนไหว)
  - อีเมลสรุปวันจันทร์ตั้งแต่ 08:00 เวลาไทย คนละ 1 ฉบับต่อสัปดาห์ (ตาราง `MailDigest` กันส่งซ้ำ ส่งไม่สำเร็จจะลองใหม่รอบถัดไป)
- **ผลการติดต่อ** (เลือกตอนบันทึกการติดต่อระดับลูกค้า เฉพาะผู้ดูแลและเฉพาะตอนลูกค้าหายไป):
  - "ยังเป็นลูกค้าอยู่" พักการเตือน 30 วัน (`dormantSnoozedUntil`) ถ้ายังไม่ซื้อจะเตือนใหม่
  - "เลิกกิจการ / ย้ายไปใช้คู่แข่ง / อื่น ๆ" เปลี่ยนสถานะเป็นเสียลูกค้า (`LOST`) เก็บเหตุผลและรายละเอียด ลูกค้าที่เสียไปออกใบเสนอราคาไม่ได้จนกว่าจะกลับมาเป็นลูกค้า (กลับมาแล้วพักการเตือน 30 วัน)
  - มีการซื้อใหม่ (Won หรือไฟล์ Express) ลูกค้าออกจากรายการเอง
- **การโอน** (`services/transfers.ts` ใช้ร่วมกันทั้งการเปลี่ยนผู้ดูแลในหน้าลูกค้า การโอนหลายราย การอนุมัติคำขอ และการโอนลูกค้าทั้งหมดของผู้ใช้):
  - ใบเสนอราคาที่ยังเปิดอยู่ (ร่าง ถึง หมดอายุ) ย้ายไปผู้ดูแลคนใหม่ เก็บผู้สร้างเดิมใน `createdById` และเวลาที่ย้ายใน `ownerSince` (หน้าใบแสดง "ผู้สร้างเดิม") ใบที่ Won/Lost/ยกเลิกแล้วยังเป็นของคนเดิม ยอด Won ก่อนวันโอนจึงยังนับให้คนเดิม
  - ผู้ดูแลคนใหม่เห็นประวัติการซื้อ (วันที่ มูลค่า สินค้า และจำนวน ไม่แสดงราคาต่อหน่วย) และบันทึกการติดต่อระดับลูกค้าของคนเดิม แต่เปิดใบเสนอราคาเก่าของคนเดิมไม่ได้ ผู้ดูแลเดิมยังเปิดใบเก่าของตัวเองได้แต่ออกใบใหม่ให้ลูกค้ารายนั้นไม่ได้
  - คำขอรับดูแลที่เปิดอยู่ของลูกค้ารายนั้นถูกปิดทั้งหมด (ของผู้รับโอนเป็นอนุมัติ ของคนอื่นเป็นไม่อนุมัติพร้อมกระดิ่ง)
  - ทั้งสองคนได้รับกระดิ่ง (โอนหลายรายพร้อมกันได้กระดิ่งสรุปคนละ 1 รายการ) บันทึก `CustomerOwnerHistory` และ audit log ทุกราย
  - การปล่อยลูกค้าไม่มีผู้ดูแลทำไม่ได้ถ้ายังมีใบเสนอราคาที่เปิดอยู่
  - ผู้บริหารและแอดมินโอนได้ทุกลูกค้า (กฎ 6 เดือนเป็นเกณฑ์ของรายการ "โอนได้" และการขอรับดูแล ไม่ได้จำกัดสิทธิ์ผู้บริหาร) แอดมินโอนลูกค้าทั้งหมดของผู้ใช้ได้จากหน้าแก้ไขผู้ใช้ (ใช้ตอนพนักงานลาออก)
- **คำขอรับดูแล** (`CustomerTransferRequest`): พนักงานขายเห็นข้อความ "ดูแลโดย คุณ X และไม่มีการซื้อเกิน N เดือน" (หรือ "ซึ่งปิดบัญชีแล้ว" / "ถูกบันทึกว่าเสียลูกค้าแล้ว") พร้อมปุ่มขอรับดูแล ระบบไม่บอกวันที่ซื้อล่าสุดหรือยอดซื้อของคนอื่น ผู้ขอ 1 คนมีคำขอที่รออยู่ได้ 1 รายการต่อลูกค้า (partial unique index) ผู้บริหารและแอดมินอนุมัติหรือไม่อนุมัติที่หน้า "คำขอรับดูแลลูกค้า" การอนุมัติ claim คำขอก่อนแล้วโอนใน transaction เดียวกัน กดซ้ำหรือผู้บริหาร 2 คนกดพร้อมกันได้ผลครั้งเดียว
- **หน้าลูกค้าที่หายไป** (`/customers/dormant`): พนักงานขายเห็นเฉพาะลูกค้าของตัวเอง (แยกรายการที่พักการเตือน) ผู้บริหาร/แอดมินเห็นสรุปจำนวนแยกตามพนักงานขาย รายที่ยังไม่มีการติดต่อตั้งแต่หายไป เหตุผลที่เสียลูกค้า และเลือกโอนหลายรายพร้อมกัน (สูงสุด 1,000 รายต่อครั้ง) export Excel และตัวกรองบริษัทเพิ่มใน M7 (ดู 0.7)
- **นำเข้าวันที่ขายล่าสุดจาก Express** (หน้านำเข้าข้อมูล แยกบริษัท): แม่แบบมีรหัสลูกค้า Express, เลขผู้เสียภาษี, รหัสสาขา, วันที่ขายล่าสุด (บังคับ) และยอดขาย 12 เดือน (ไม่บังคับ) จับคู่ด้วยรหัส Express ของบริษัทนั้นก่อน แล้วจึงเลขภาษี + สาขา รหัสกับเลขภาษีชี้คนละรายเป็นข้อผิดพลาด อ่านวันที่ได้ทั้งช่องวันที่ของ Excel, วัน/เดือน/ปี ค.ศ. หรือ พ.ศ. และเลข serial ของ Excel วันที่เก่ากว่าที่นำเข้าไว้แล้วไม่ถูกใช้ แถวที่ไม่พบลูกค้าแสดงในหน้าตรวจไฟล์ บันทึกด้วย `INSERT … ON CONFLICT` และ `UPDATE … FROM unnest(...)` ทีละ 1,000 แถว **เมื่อได้ไฟล์จริงจาก Express (กำหนด 26 พ.ย.) ต้องตรวจชื่อคอลัมน์และรูปแบบวันที่อีกครั้ง**
- **งานรายวัน**: เปลี่ยนชื่อเป็น `POST /api/cron/daily` รวมงานใบเสนอราคา (หมดอายุ, เตือน 7 วัน) และงานลูกค้า (กระดิ่งลูกค้าหายไป, อีเมลวันจันทร์) `?digest=now` ส่งอีเมลของสัปดาห์นั้นทันทีให้คนที่ยังไม่ได้รับ (ใช้ทดสอบหรือส่งด้วยมือ)
- **ฐานข้อมูล**: CHECK constraint บังคับว่าลูกค้าที่เสียไปต้องมีเหตุผลและวันที่, คำขอที่ตัดสินแล้วต้องมีผู้ตัดสินและเวลา, เหตุผลของคำขอต้องไม่ว่าง, ยอดขาย Express ต้องไม่ติดลบ migration เติม `lastPurchaseDate` จากใบที่ Won อยู่แล้ว
- **ข้อมูล Express แยกรายบริษัท**: ตาราง `CustomerExpressSale` เก็บวันที่ขายล่าสุดและยอดขาย 12 เดือนต่อ (ลูกค้า, บริษัท) ไฟล์ของบริษัทหนึ่งจึงไม่เขียนทับของอีกบริษัท ยอด 12 เดือนเปลี่ยนเฉพาะเมื่อวันที่ขายของบริษัทนั้นใหม่กว่าเดิม (ไฟล์เดือนถัดไปที่วันขายเท่าเดิมคงยอดเดิม) ค่าในตาราง `customer` คือวันที่ล่าสุดของทุกบริษัท และผลรวมยอดของบริษัทที่ขายภายใน 12 เดือนก่อนวันนั้น
- **การตัดสินใจที่คงไว้และบันทึกไว้**:
  - อีเมลสรุปวันจันทร์เป็นภาษาไทยเหมือนอีเมลระบบอื่น
  - พนักงานขายขอรับดูแลลูกค้าของคนอื่นที่บันทึกว่าเสียไปแล้วได้ (ผู้บริหารเป็นคนตัดสิน)
  - แอดมินพิจารณาคำขอได้เหมือนผู้บริหาร แต่กระดิ่งคำขอใหม่ส่งถึงผู้บริหารเท่านั้น
  - ตัวเลือกลูกค้าในหน้าสร้างใบเสนอราคาแสดงเฉพาะลูกค้าที่ออกใบได้ การขอรับดูแลจึงเริ่มจากหน้าลูกค้า
  - แจ้งการโอนและผลคำขอทางกระดิ่งเท่านั้น ไม่ส่งอีเมล
  - ตัวเลข "ยังไม่ติดต่อ" ในหน้าผู้บริหารนับรายที่ยังไม่มีการติดต่อตั้งแต่ลูกค้าหายไป (รวมรายที่ไม่เคยติดต่อเลย) เพราะใช้ตัดสินใจโอนได้ตรงกว่า
  - ประวัติการซื้อและยอดซื้อเดิมเห็นเฉพาะผู้ดูแลและผู้บริหาร แอดมินที่ไม่มีบทบาทผู้บริหารไม่เห็น (สอดคล้องกับ 0.2)
- **ผลตรวจ BintzIT รอบ M6** (ไม่พบระดับ critical/high มีระดับกลาง 6 ข้อ แก้แล้วทั้งหมด):
  - **ยอด Express ถูกเขียนทับข้ามเดือนและข้ามบริษัท**: แก้ด้วยการเก็บแยกรายบริษัทตามข้างต้น
  - **Won ไม่ทำให้ลูกค้าที่เสียไปกลับมา**: กด Won แล้วลูกค้ากลับเป็นปกติ (audit `customer.reactivate` ที่มา won) และการนำเข้าใช้วันที่ในไฟล์เทียบกับวันที่บันทึกว่าเสียไป
  - **deadlock**: การกด Won และการอนุมัติคำขอล็อกแถวลูกค้าก่อน ลำดับเดียวกับการโอน (ลูกค้า → ใบเสนอราคา/คำขอ)
  - **การโอนจำนวนมาก**: เขียนเป็นคำสั่งแบบชุด (คำสั่งไม่กี่คำสั่งต่อการโอนหนึ่งครั้ง) และ "โอนทั้งหมด" โอนเฉพาะลูกค้าที่ยังเป็นของคนนั้นภายใต้ lock
  - **ใบเสนอราคาค้างของคนที่ลาออก**: "โอนทั้งหมด" ย้ายใบที่ยังเปิดอยู่ของคนนั้นซึ่งลูกค้าเป็นของคนอื่นแล้ว ไปให้ผู้ดูแลปัจจุบันของลูกค้า (หรือผู้รับโอนถ้าผู้ดูแลไม่ได้ใช้งานแล้ว)
  - **แอดมินเห็นมูลค่า Won**: ซ่อนตามข้างต้น
  - ระดับต่ำ: ป้ายเมนูบอกว่าเป็นจำนวนคำขอ, ปุ่มแท็บสูงพอแตะบนมือถือ, แถบล่างจอบนมือถือเมื่อเลือกลูกค้า, หน้าต่างยืนยันก่อนโอนหลายราย/โอนทั้งหมด/อนุมัติ, ไม่แจ้งเตือนซ้ำ, อ่านวันที่ที่มีเวลาต่อท้ายได้, ยอดขายที่อ่านไม่ได้ไม่ทำให้ทิ้งวันที่ขาย, ลิงก์ "คำขอรับดูแลลูกค้าของฉัน" และถ้อยคำภาษาอังกฤษ
  - **ตรวจซ้ำ**: ข้อระดับกลางแก้ถูกต้องครบ และแก้ระดับต่ำที่พบเพิ่ม 4 ข้อ ได้แก่ กด Enter ในช่องหมายเหตุไม่ข้ามหน้าต่างยืนยัน, ผู้ได้รับใบเสนอราคาค้างได้กระดิ่ง, ยอด 12 เดือนจาก Express รวมเฉพาะบริษัทที่ขายภายใน 12 เดือนก่อนวันขายล่าสุด, งานรายวันและการนำเข้าล็อกลูกค้าเรียงตาม id ส่วนข้อมูลทดสอบในเครื่องพัฒนาที่นำเข้าด้วยโค้ดรุ่นแรกไม่ถูกย้ายเข้าตารางใหม่ (ไม่กระทบ production เพราะยังไม่เคยขึ้นจริง)

## 0.7 การตัดสินใจระหว่างทำ M7

- **ตัดสินใจร่วมกับผู้ใช้ (25 พ.ย. 2026)**:
  - "มูลค่าที่เสนอ" นับเข้าเดือนตามวันที่ส่งลูกค้า **ครั้งแรก** (ไม่ว่าจะมีกี่ revision) ใช้มูลค่าล่าสุดของใบ ใบที่ยังไม่ส่งและใบที่ยกเลิกไม่นับ
  - อัตราปิดการขาย = Won ÷ (Won + ไม่ได้งาน + หมดอายุ) ของใบที่ปิด/หมดอายุในช่วงนั้น แสดงทั้งตามมูลค่าและตามจำนวนใบ ไม่มีใบปิดเลยแสดง "—"
  - เป้ายอดขาย 1 ตัวเลขต่อพนักงานขายต่อเดือน (ก่อน VAT รวมทุกบริษัท) ผู้บริหารหรือแอดมินตั้งที่หน้า "เป้ายอดขาย" ทีละปี
  - Excel รายการ Won สำหรับฝ่ายบัญชี 1 แถวต่อ 1 บรรทัดสินค้า และมีชีตสรุปต่อใบ
- **นิยามตัวเลข** (`domain/reports.ts` และ `services/reports.ts` ใช้ชุดเดียวกันทั้งแดชบอร์ด รายงาน และ Excel):
  - ทุกมูลค่าเป็นยอดก่อน VAT (`afterDiscountSatang`) เดือนและวันเป็นเวลาไทย
  - มูลค่าที่เสนอนับให้คนที่ส่งครั้งแรก (`quotation.firstSentAt`, `firstSentById` ตั้งตอนส่งครั้งแรก ไม่เปลี่ยนเมื่อทำ revision หรือโอน migration เติมจาก revision แรกที่ส่ง) ใบที่โอนไปแล้วจึงยังนับมูลค่าที่เสนอให้คนเดิม
  - Won และไม่ได้งานนับตาม `closedAt` ให้เจ้าของใบ (ใบที่ปิดแล้วไม่ย้ายตอนโอน) หมดอายุนับตาม `expiredAt` ใบที่ทำ revision หลังหมดอายุจะไม่ถูกนับเป็นหมดอายุอีก ตัวเลขย้อนหลังของเดือนที่ผ่านมาจึงเปลี่ยนได้เมื่อมีการแก้ไขใบ
  - เป้าเทียบกับ Won เท่านั้น และเทียบเฉพาะ Won ของคนที่ตั้งเป้าไว้ในเดือนนั้น (ถ้าตั้งไม่ครบทุกคนจะแสดงว่าเทียบกี่คนจากทั้งหมด) เมื่อเลือกบริษัทจะไม่เทียบเป้า (เพราะเป้าตั้งรวมทุกบริษัท) ไม่ได้ตั้งเป้าแสดง "ยังไม่ได้ตั้งเป้า" ไม่ใช่ 0%
  - ตารางแยกพนักงานขายแสดงพนักงานขายที่ใช้งานอยู่ทุกคน และคนที่ปิดบัญชีแล้วถ้ามีตัวเลขหรือเป้าในเดือนนั้น
  - รายงานกรองตามวันที่ได้ 3 แบบ: ส่งครั้งแรก (ตรงกับมูลค่าที่เสนอ ไม่รวมใบที่ยกเลิกเว้นแต่เลือกสถานะยกเลิก) / ปิดงานหรือหมดอายุ (ตรงกับ Won) / วันที่สร้าง ผู้บริหารที่เลือกพนักงานขายในแบบส่งครั้งแรกจะได้ใบตามผู้ที่ส่งครั้งแรก (ตรงกับแดชบอร์ด) ส่วนพนักงานขายเห็นเฉพาะใบที่ยังเป็นของตัวเอง ใบที่โอนไปแล้วจึงนับในแดชบอร์ดแต่ไม่อยู่ในรายงานของคนเดิม (หน้ารายงานแจ้งไว้) ช่วงวันที่ยาวเกิน 2 ปีถูกตัดและแจ้งผู้ใช้
  - สินค้าและลูกค้าที่เสนอบ่อยเรียงตามจำนวนใบ แล้วจึงตามมูลค่า
  - **ตัวเลขย้อนหลังที่ยังเปลี่ยนได้ (ยอมรับไว้)**: ใบที่หมดอายุแล้วทำ revision จะไม่นับเป็นหมดอายุอีก และใบหมดอายุของลูกค้าที่ถูกโอนจะย้ายไปผู้ดูแลใหม่ (กฎการโอนของ M6) อัตราปิดการขายของเดือนที่ผ่านมาจึงเปลี่ยนได้ ส่วนมูลค่าที่เสนอ ยอด Won และการเทียบเป้าย้อนหลังไม่เปลี่ยน ถ้าต้องการให้คงที่ ต้องเก็บเหตุการณ์หมดอายุแยกเป็นตาราง
  - "ลูกค้าของบริษัท" (ตัวกรองบริษัทของลูกค้าที่หายไปและตัวเลขบนแดชบอร์ด) = ลูกค้าที่มีข้อมูลขายจาก Express ของบริษัทนั้น หรือเคยได้รับใบเสนอราคาของบริษัทนั้น เพราะลูกค้าใช้ร่วมกันทุกบริษัท
- **สิทธิ์**: พนักงานขายเห็นแดชบอร์ด รายงาน และ Excel เฉพาะของตัวเอง (ค่า `owner` ใน URL ถูกแทนด้วยผู้ใช้ที่ล็อกอินเสมอ ใช้ตัวอ่านตัวกรองเดียวกันทั้งหน้าและ route export) ผู้บริหารเห็นทั้งหมด แอดมินที่ไม่มีบทบาทผู้บริหารไม่เห็นยอดขาย (ไม่มีแดชบอร์ด รายงาน export ยอด และรายละเอียดก่อน/หลังของใบเสนอราคาใน audit log) แต่ตั้งเป้าและดู audit log ได้ตามข้อ 10 ของ requirements
- **หน้าใหม่**: `/dashboard` (พนักงานขาย ผู้บริหาร), `/reports` + `/api/reports/{quotations,won-lines,dormant}` (Excel, ไม่เกิน 20,000 รายการต่อไฟล์ เกินแล้วแจ้งให้กรองให้แคบลง ไม่ตัดข้อมูลทิ้งเงียบ ๆ), `/targets` (ผู้บริหาร แอดมิน ลิงก์จากแดชบอร์ดและหน้าตั้งค่า), `/audit` (ผู้บริหาร แอดมิน แบ่งหน้าแบบ cursor ตามเวลา)
- **กราฟ**: วาดเป็น SVG ฝั่ง server ไม่เพิ่ม library สีจาก palette มาตรฐานที่ตรวจสำหรับตาบอดสีแล้ว (เสนอ = น้ำเงิน, Won = ส้ม, เป้า = เส้นประ) มีตารางตัวเลขเดียวกันให้เปิดดูใต้กราฟ
- **ประวัติในหน้าใบเสนอราคา**: เจ้าของใบและผู้บริหารเห็นว่าใครทำอะไรเมื่อไหร่ แสดงรายละเอียดเฉพาะฟิลด์ที่อนุญาต (สถานะ เหตุผล หมายเหตุ PO ช่องทาง ผู้รับอีเมล) ไม่แสดง IP และรายละเอียดราคาในคำขออนุมัติ ผู้บริหารมีลิงก์ไปดู audit log แบบละเอียด
- **Excel**: ตัวเลขเป็นตัวเลขจริง (ไม่ใช่ข้อความ) แถวรวมเว้นจากข้อมูล 1 แถวและเป็นสูตร `SUBTOTAL(109, …)` ที่มีผลลัพธ์ในไฟล์ (ตามตัวกรองของ Excel) ชื่อไฟล์ภาษาไทยด้วย `filename*=UTF-8''` ไม่ cache ชีตสรุป Won ต่อใบตรวจว่าผลรวมบรรทัด (หลังกระจายส่วนลดท้ายบิล) เท่ากับยอดก่อน VAT ของใบ
- **แก้ปัญหาเวลา (time zone) ของการเชื่อมต่อฐานข้อมูล**: Prisma adapter-pg ส่งและอ่านเวลาเป็นค่า UTC ที่ไม่มีโซน ถ้า session ของ PostgreSQL ไม่ใช่ UTC (ฐานข้อมูลในเครื่องพัฒนาตั้งเป็น Asia/Bangkok) เวลาทุกค่าจะถูกเก็บคลาดไป 7 ชั่วโมง และ SQL ที่แปลงเวลาด้วย `AT TIME ZONE` (เดือนในรายงาน วันที่ซื้อล่าสุด) จะผิด แก้โดยบังคับ `TimeZone=UTC` ในการเชื่อมต่อ (`server/db.ts` และ seed) ตั้งค่าเริ่มต้นของฐานข้อมูลเป็น UTC ด้วย migration (`ALTER DATABASE … SET timezone`) สำหรับการเชื่อมต่อผ่าน pooler ที่ไม่รับ startup options และส่งเวลาใน raw SQL ผ่าน `instant()` (`server/sql.ts`) ข้อมูลในเครื่องพัฒนาที่บันทึกก่อนแก้ยังคลาดอยู่ 7 ชั่วโมง (production ยังไม่เคยใช้งาน)
- **ผลตรวจ BintzIT รอบ M7** (ไม่พบระดับ critical และไม่พบการข้ามสิทธิ์ ทดสอบสิทธิ์จริงทุกหน้าและทุก route แล้ว มีระดับสูง 2 ข้อ กลาง 5 ข้อ ต่ำ 7 ข้อ):
  - **ร้อยละเทียบเป้าสูงเกินจริงเมื่อบางคนไม่มีเป้า** (สูง): เทียบเฉพาะ Won ของคนที่มีเป้าตามข้างต้น ตารางใต้กราฟเพิ่มคอลัมน์ร้อยละเทียบเป้ารายเดือน
  - **รายงานแบบส่งครั้งแรกไม่ตรงกับแดชบอร์ด** (สูง): ไม่รวมใบยกเลิก และผู้บริหารกรองตามผู้ส่งครั้งแรก ตามข้างต้น
  - หัวไฟล์ Excel รายการ Won ระบุว่านับตามวันที่ได้งานและไม่แสดงตัวกรองสถานะที่ไม่ได้ใช้
  - ค้นหาเลขผู้เสียภาษีที่มีขีดไม่พบ (regex ผิด) แก้แล้ว
  - ประวัติในหน้าใบเสนอราคาแสดงวันที่ ช่องทาง และเหตุผลเป็นคำ ไม่ใช่รหัส เหตุผลที่ระบบเขียนเก็บเป็นรหัสแล้วแปลตอนแสดง
  - การตั้ง time zone ผ่าน startup options อาจใช้ไม่ได้กับ pooler: เพิ่ม migration ตั้งค่าของฐานข้อมูลตามข้างต้น
  - ตัวเลขย้อนหลังของใบหมดอายุ: บันทึกเป็นข้อจำกัดที่ยอมรับไว้ตามข้างต้น
  - ระดับต่ำ: คำว่า "รวม" ใน Excel แปลตามภาษา, ลิงก์ export ไม่ใช้ `download` เพื่อให้เห็นข้อความเมื่อข้อมูลเกิน และจำกัดจำนวนบรรทัดสินค้าใน Excel Won ที่ 100,000 บรรทัด, บันทึกเป้าเขียนเฉพาะช่องที่ผู้ใช้แก้ (คนอื่นบันทึกพร้อมกันไม่ถูกเขียนทับ), เรียงสินค้าและลูกค้าตามความถี่, เมนูประวัติการแก้ไขสำหรับผู้บริหาร, แจ้งเมื่อช่วงวันที่ถูกตัด, ถ้อยคำภาษาไทยที่เป็นทางการขึ้น

- **โครงหน้า**: เมนูด้านซ้าย `AppSidebar` (`components/app-nav.tsx`) แบ่งหมวด ภาพรวม / งานขาย / ลูกค้าและสินค้า / การจัดการหรือระบบ ตามบทบาท ตัวเลขคำขออนุมัติและคำขอโอนแสดงเป็นป้ายตัวเลข (มี `aria-label`) ปุ่ม "สร้างใบเสนอราคา" อยู่บนสุดสำหรับพนักงานขาย ต่ำกว่า `lg` เป็นเมนูเลื่อนออก (`MobileNav`) แถบบนเหลือกระดิ่งและเมนูผู้ใช้ ไอคอนส่งจาก server เป็นชื่อ (ส่ง component ข้าม server/client ไม่ได้)
- **สัญลักษณ์แบรนด์**: `components/brand-mark.tsx` เป็นตัวอักษร "JCP" สีแดงพร้อมเส้นโค้งเขียวมะนาวบนพื้นขาว ใช้ชั่วคราวจนกว่าจะได้ไฟล์โลโก้ต้นฉบับ
- **คอมโพเนนต์ร่วม**: ปุ่ม ช่องกรอก การ์ด ตาราง (หัวตารางพื้นเทา) และ `FormSection` เป็นการ์ดพื้นขาวบนพื้นหลังเทาอ่อน, `PageHeader` รับ `description`, `EmptyState` สำหรับรายการว่าง, `StatusBadge` มีจุดสีและข้อความกำกับ (ไม่สื่อด้วยสีอย่างเดียว), ตัวกรองแบบ GET อยู่ในการ์ด
- **หน้าแรก**: คำทักทายตามเวลาไทย ทางลัด การ์ดสรุป 3 ใบ (ต้องติดตาม / ใบที่เงียบ / ลูกค้าที่หายไป) และรายการงานในการ์ด
- **หน้าเข้าสู่ระบบ / 2FA / ลืมรหัสผ่าน**: แบ่งสองฝั่ง ฝั่งซ้ายเป็นแผงแบรนด์ (เฉพาะจอกว้าง) ฝั่งขวาเป็นฟอร์ม
- **มือถือ**: รายการใบเสนอราคาแสดงเป็นการ์ดต่ำกว่า `sm` (ตารางเดิมยังใช้ตั้งแต่ `sm` ขึ้นไป) และเคารพ `prefers-reduced-motion`
- **ตรวจแล้ว**: typecheck, lint, unit test 196 ข้อ และตรวจในเบราว์เซอร์ทั้งเดสก์ท็อป/มือถือ ไทย/อังกฤษ บทบาทพนักงานขายและแอดมิน (รวมเข้าสู่ระบบด้วย 2FA)
- **ข้อสังเกตตอนพัฒนา**: dev server อาจส่ง HTML เก่าของหน้า static (เช่น `/forgot-password`) หลังแก้ layout ให้รีสตาร์ต `npm run dev` ถ้าเห็นหน้าตาเดิม

### เรื่องที่ต้องทำก่อนขึ้น production (M8)

- **ตั้งค่า IP ของ proxy**: ตั้ง `advanced.ipAddress` ของ Better Auth ให้ตรงกับ proxy ของ Render และให้ `server/audit.ts` อ่าน IP ด้วยวิธีเดียวกัน ถ้าไม่ตั้ง ผู้โจมตีปลอม header `X-Forwarded-For` เพื่อเลี่ยง rate limit และปลอม IP ใน audit log ได้
- **ข้อความ "บัญชีถูกล็อก" บอกว่าอีเมลมีอยู่จริง**: รับได้สำหรับระบบภายใน แต่ถ้าต้องการปิด ให้ใช้ข้อความเดียวกับ "อีเมลหรือรหัสผ่านไม่ถูกต้อง"
- **ที่เก็บไฟล์**: ตั้ง `STORAGE_DIR` เป็น persistent disk ของ Render หรือเพิ่ม driver Cloudflare R2 ใน `storage.ts` เพราะดิสก์ปกติของ container หายทุกครั้งที่ deploy
- **Docker**:
  - ติดตั้ง Chromium และตั้ง `CHROME_PATH`
  - container รันเป็น root จึงใช้ `--no-sandbox` (หน้าที่พิมพ์ถูกปิด JavaScript และ network อยู่แล้ว) หรือรันเป็น user ปกติแล้วเปิด sandbox
- **`.dockerignore`**: ต้องไม่ใส่ `.env`, `.dev-credentials.txt`, `storage/` เข้า image เพราะ Next จะคัดลอก `.env` ที่มีอยู่เข้า `.next/standalone`
- **Resend**: สมัครบัญชี ยืนยัน 2 โดเมน (SPF/DKIM) ตั้ง `RESEND_API_KEY` และ `MAIL_FROM` แล้วทดสอบส่งจากทั้ง 2 บริษัทที่ใช้คนละโดเมน
- **ตรวจ dependency** (`npm audit`): ช่องโหว่ที่เหลืออยู่ใน Prisma CLI, shadcn CLI (ใช้ตอนพัฒนา) และ exceljs (uuid) ให้ตรวจอีกครั้งก่อนขึ้นจริง
- **Render Cron Jobs**: ตั้ง `CRON_SECRET` (สุ่มอย่างน้อย 32 ตัวอักษร) ทั้งในเว็บและใน cron แล้วเรียกด้วย `curl -X POST -H "Authorization: Bearer $CRON_SECRET" https://<โดเมน>/api/cron/<ชื่องาน>`
  - `approval-reminders` ทุก 15 นาที
  - `daily` ทุกชั่วโมง (อย่างน้อยวันละครั้งหลังเที่ยงคืนเวลาไทย และ 1 ครั้งหลัง 08:00 วันจันทร์) สำหรับใบหมดอายุ เตือนใบที่ไม่มีการติดตาม กระดิ่งลูกค้าที่หายไป และอีเมลสรุปลูกค้าที่หายไปวันจันทร์
- **`MAIL_FROM`**: ต้องตั้งเป็นผู้ส่งของอีเมลระบบ (ลืมรหัสผ่าน แจ้งการอนุมัติ) เช่น `"Quotation JCP" <no-reply@โดเมน>` และ `APP_URL` เป็นโดเมนจริง เพราะลิงก์ในอีเมลใช้ค่านี้
- **โลโก้ JCP ต้นฉบับ**: แทนสัญลักษณ์ชั่วคราวใน `components/brand-mark.tsx` ด้วยไฟล์จริง (SVG หรือ PNG พื้นโปร่งใส) และใส่ภาพหน้าจอดีไซน์ใหม่ในคู่มือผู้ใช้
- **วันหยุดนักขัตฤกษ์**: ถ้าต้องการให้การเตือนไม่นับวันหยุด ให้เพิ่มรายการวันหยุดใน `business-hours.ts` หรือหน้าตั้งค่า

## 0.9 การตัดสินใจระหว่างทำ M8 (ขึ้นระบบจริง)

ขั้นตอนขึ้นระบบทั้งหมดอยู่ใน [deploy.md](deploy.md)

- **ผู้ใช้เลือก (26 พ.ย. 2026)**: ไฟล์เก็บบน Render Persistent Disk (ไม่ใช้ R2), เว็บขนาด Standard 1 CPU / 2 GB, สำรองข้อมูลด้วยระบบของ Render พร้อมซ้อมกู้คืนเดือนละครั้ง, บริษัทนำร่องและโดเมนแจ้งภายหลัง จึงทำส่วนในเครื่องก่อน
- **ผลของการใช้ดิสก์**: รันได้ 1 instance และระหว่าง deploy ระบบหยุดชั่วครู่ (Render หยุดเวอร์ชันเก่าก่อน) จึงปิด auto deploy และ deploy นอกเวลาทำงาน
- **Docker image** (`Dockerfile`):
  - 3 stage บน `node:24-bookworm-slim` ติดตั้ง openssl ตั้งแต่ stage ติดตั้ง dependency เพื่อให้ Prisma ได้ engine รุ่น OpenSSL 3 ตรงกับตอนรัน
  - stage สุดท้ายมี Chromium (+ ฟอนต์ไทยสำรอง), แอปแบบ standalone ที่ `/app` และเครื่องมือ migration/seed/ตรวจฐานข้อมูลที่ `/opt/tools`
  - `.dockerignore` กัน `.env*`, `.dev-credentials.txt`, `storage/` ไม่ให้เข้า image (Next คัดลอก `.env` เข้า `.next/standalone` ถ้ามีอยู่ตอน build)
  - `deploy/entrypoint.sh` เริ่มเป็น root เพื่อมอบโฟลเดอร์บนดิสก์ (Render mount เป็นของ root) ให้ user `node` แล้วลดสิทธิ์ด้วย `setpriv` และตั้ง `HOME` ใหม่ Chromium ยังใช้ `--no-sandbox` (หน้าที่พิมพ์ปิด JavaScript และ network อยู่แล้ว)
- **Render Blueprint** (`render.yaml`): เว็บ Docker + ดิสก์ 5 GB ที่ `/var/data`, PostgreSQL 17 ปิดการเชื่อมต่อจากภายนอก, region Singapore, pre-deploy รัน `prisma migrate deploy`, cron 2 งานเป็น Node ธรรมดาที่เรียก `deploy/cron.mjs` (อ่าน secret จาก env ไม่อยู่ในบรรทัดคำสั่ง) ค่า `APP_URL` / `CRON_SECRET` ของ cron อ้างจากเว็บด้วย `fromService` จึงต้อง Blueprint Sync หลังเปลี่ยนค่า
- **ไม่ยอมเริ่มทำงานเมื่อค่าไม่ครบ** (`src/server/startup-check.ts` ผ่าน `src/instrumentation.ts`): ตรวจ `DATABASE_URL`, secret ยาว ≥ 32, `APP_URL`/`BETTER_AUTH_URL` เป็น https โดเมนเดียวกัน, `STORAGE_DIR` เป็น path เต็ม (บน Render ต้องอยู่ใต้ `/var/data/`), Resend, `MAIL_FROM`, `CRON_SECRET` แล้ว `process.exit(1)` เพราะการ throw ใน `register` ทำให้ Next ยังรับคำขอแต่ตอบ 500 ทุกหน้า ใช้ `ALLOW_INCOMPLETE_ENV=1` ได้เฉพาะทดสอบในเครื่อง
- **IP ผู้ใช้** (`src/server/domain/client-ip.ts`): เอกสาร Render ไม่ระบุ header ที่เชื่อถือได้ จึงตั้งได้ด้วย `CLIENT_IP_HEADER` (header เดี่ยวที่ proxy เขียนทับ ใช้ทั้ง rate limit ของ Better Auth และ audit log) หรือ `TRUSTED_PROXY_HOPS` (นับ `X-Forwarded-For` จากขวา ใช้กับ audit log เท่านั้น) ค่าเริ่มต้นไม่เชื่อค่าซ้ายสุดที่ผู้ใช้ปลอมได้อีกต่อไป ตรวจบนระบบจริงด้วย `POST /api/ops/ip-check` (ต้องใช้ `CRON_SECRET`) ก่อนตั้ง `CLIENT_IP_HEADER` rate limit การเข้าสู่ระบบนับรวมทุกคน
- **`/api/health`**: สาธารณะ ตอบเฉพาะ ok/ไม่ ok ของฐานข้อมูล เขตเวลา session และสิทธิ์เขียนดิสก์ (ไม่เขียนไฟล์) Render ใช้เป็น health check เขตเวลาระดับฐานข้อมูลตรวจด้วย `deploy/db-check.mjs` ใน Shell ของเว็บ (Render Postgres ไม่มี Shell)
- **Security headers** (`next.config.ts`): `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, CSP เฉพาะ `frame-ancestors / base-uri / form-action / object-src` (ไม่จำกัด script เพราะต้องใช้ nonce กับ Next), HSTS 1 ปีใน production (ไม่ใส่ includeSubDomains), ปิด `X-Powered-By` ตรวจแล้วว่า PDF แบบ inline และ server action ยังทำงาน
- **ตรวจ dependency** (`npm audit --omit=dev`): เหลือ moderate/high ใน Prisma CLI (effect), shadcn CLI (ts-morph, minimatch) ซึ่งใช้ตอนพัฒนา/migration ไม่รับข้อมูลจากผู้ใช้ และ exceljs → uuid ซึ่งช่องโหว่อยู่ใน v3/v5/v6 แบบส่ง buffer แต่ exceljs ใช้เฉพาะ `v4()` จึงไม่กระทบ ไม่รัน `npm audit fix --force` เพราะจะลดรุ่น exceljs/prisma
- **ทดสอบ**: unit test 203 ข้อ, `tests/smoke/m8-security.mjs` 45/45 บน dev server และ 44/44 บน production build (`next start` แบบ standalone), smoke M3/M4/M7 ผ่านซ้ำ, ทดสอบว่า standalone ไม่ยอมเริ่มเมื่อค่าไม่ครบ
- **ผลตรวจ BintzIT รอบ M8**: สูง 2 ข้อ (Prisma engine ไม่ตรงรุ่น OpenSSL, คำสั่ง seed ในคู่มือหา `tsx` ไม่เจอ), กลาง 5 ข้อ (HOME หลังลดสิทธิ์, `TRUSTED_PROXY_HOPS` ไม่มีผลกับ rate limit, คู่มือเรื่องระบบหยุดเมื่อค่าผิด, ไม่มี Shell ของฐานข้อมูล, URL onrender.com อาจไม่ตรงชื่อ), ต่ำ 8 ข้อ แก้ครบทุกข้อ
- **ทดสอบ Docker image ในเครื่อง (26 พ.ย. 2026)**: image 2.8 GB มี `schema-engine-debian-openssl-3.0.x`, ไม่มี `.env` หรือ secret ติดมา, `migrate.sh` รัน migration ครบกับ PostgreSQL 17, `db-check.mjs` ได้เขตเวลา UTC, แอปรันเป็น user `node` (uid 1000) และเขียนดิสก์ที่ mount เป็นของ root ได้, health ok, seed แอดมินด้วยคำสั่งในคู่มือได้, Chromium ใน container พิมพ์ PDF ภาษาไทยถูกต้อง, ชุดทดสอบความปลอดภัยแบบไม่ล็อกอินผ่าน (รวม HSTS), ไม่ยอมเริ่มเมื่อขาด Resend หรือ `STORAGE_DIR` อยู่นอก `/var/data/`, ไฟล์อยู่ครบหลังรีสตาร์ท container
- **หน่วยความจำตอน build**: Turbopack เปิด worker ตามจำนวน CPU บนเครื่องที่ CPU มากแต่หน่วยความจำน้อย (Docker Desktop ค่าเริ่มต้น 2 GB, 20 CPU) build ล่มหรือค้าง จึงจำกัด `TOKIO_WORKER_THREADS` / `RAYON_NUM_THREADS` = 4 และ heap 1.5 GB ในขั้น build และต้องให้ Docker Desktop มีหน่วยความจำอย่างน้อย 8 GB เมื่อ build ในเครื่อง
- **เรื่องที่ยังเปิดอยู่**: ข้อความ "บัญชีถูกล็อก" ยังบอกว่าอีเมลมีอยู่จริง (ยอมรับได้สำหรับระบบภายใน), โลโก้ JCP ต้นฉบับ, วันหยุดนักขัตฤกษ์, ข้อมูลในเครื่องพัฒนาที่บันทึกก่อนแก้เขตเวลายังคลาดเคลื่อน 7 ชั่วโมง (ไม่กระทบ production ที่เริ่มจากฐานข้อมูลใหม่)

| ทดสอบ | **Vitest** (กฎราคา / สิทธิ์ / เลขที่) + **Playwright** (ไล่หน้าจอจริง) | |
| ที่วางระบบ | **Docker บน Render (สิงคโปร์)** + Render PostgreSQL | ไม่ติดข้อจำกัด serverless เรื่อง Chromium และงานตามเวลา |

## 4. กฎที่ต้องบังคับที่ฝั่ง server (ห้ามพึ่งหน้าจอ)

- **สิทธิ์การมองเห็น**: ทุก query ของพนักงานขายต้องกรองตามผู้ใช้ที่ล็อกอิน (กันการเปลี่ยนเลขใน URL เพื่อดูใบของคนอื่น)
- **ราคาขั้นต่ำ**: ไม่ส่งออกไปหน้าจอของพนักงานขายเลย ส่งแค่ธง "ต้องขออนุมัติ" (ระวัง Server Components ส่ง object ทั้งก้อนไปฝั่ง browser)
- **เจ้าของลูกค้า**: เช็คตอนสร้างและตอนบันทึกใบเสนอราคา
- **คำนวณราคา**: คิดใหม่ที่ server ทุกครั้ง ไม่เชื่อตัวเลขที่ส่งมาจากหน้าจอ
- **ออกเลขที่เอกสาร**: ทำใน transaction เดียวกับการบันทึก
- **Server Actions / API**: ทุกตัวตรวจ session + บทบาท + ตรวจข้อมูลด้วย Zod
